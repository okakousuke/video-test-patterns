# RawInspector

`video-test-patterns` が生成したRAWを、manifestとセットで**検査する**ためのWPFアプリです。

[`RawManifestViewer`](../RawManifestViewer/)（Windows Forms）の後継にあたります。
あちらは「生成したRAWを開いて見る」ためのものでした。こちらは、画素のコード値・変換条件・中間データまで踏み込んで確認することを目的にしています。

## 変換の途中を出す（フェーズ2）

**手順を文章で書くだけでは、どの段で何が変わったのかは分かりません。**
右下の説明は「そう書いてある」だけで、絵になっているのは最後の結果1枚だけでした。
色がずれているときに、色差を戻した段の話なのか、正規化の段なのか、matrix の段なのかを
切り分けられるように、各段で止めた値をそのまま絵にします。

| 段 | 画面に出るもの |
| --- | --- |
| 1. コード値（格納されたまま） | 取り出した値そのもの。色差はまだ間引かれたまま |
| 2. 色差を戻したあと | 輝度と同じ密度へ戻した直後 |
| 3. 正規化したあと | Y は 0-1、Cb・Cr は ±0.5 |
| 4. RGBへ戻した直後（丸める前） | 0-1 の外へ出た値がまだ残っている |
| 5. 8bitへ量子化（既定） | いつもの表示 |

**並ぶ段はRAWによって変わります**（`PipelineStages.For`）。4:4:4 に色差を戻す段はありませんし、
RGB には正規化と matrix の段がありません。切り替えても絵が変わらない段を並べると、
「効いていない」のか「そういう段」なのかが区別できなくなります。

段ごとに値の意味が違うので、画にする方法も違います。1・2段目は成分を1つに絞れば
その面のコード値がそのまま濃淡になり（「コード値」の指定と同じ絵です）、2つ以上なら
3つの値を R・G・B の位置へ置きます。3段目は Cb・Cr が 0 を中心に振れるので +0.5 してから濃淡にします。
**どちらも色としての意味はありません。** 選んだ段の写し方は、絵の上に毎回出します。

4段目と5段目は、絵そのものは同じです。出すときには結局 0-1 へ丸めるためで、
違いは「範囲外」を出したときに見えます。

### 範囲外（クリップ）の示し方

丸めたあとの絵では、0 未満も 1 超も同じ黒・同じ白になります。潰れた場所は
丸める前を見ないかぎり分かりません。「範囲外」を押すと、赤（上へ外れた）・青（下へ外れた）・
マゼンタ（成分によって上下どちらへも）で色が付きます。

**絵のほうは無彩色にします。** 元の色を残したまま色を重ねると、もともと赤い画素と
範囲外だから赤くした画素が見分けられません。無彩色の上なら、飽和した赤・青・マゼンタは
この表示でしか出ません。

押せるのは3段目以降だけです。1・2段目のコード値は格納できる範囲の中にしか入らないので
（0-255 や 0-1023 を超える値は書き込めません）、範囲外という状態が存在しません。
出ようがないものに口を残すと、「範囲外が無い」のか「機能が効いていない」のかが区別できなくなります。

数えはじめる幅は**画面の1コード値（1/255）**です。0 を少しでも外れたら数える、にはできません。
正常なカラーバーが一面に光ります。生成側は RGB から Y'CbCr を作るときに整数へ丸めているので、
戻すと必ず端数が出るためです。

手元の 8bit limited / BT.709 カラーバー（`samples/raw`）で測った値です。

| 読み方 | はみ出しの最大 | 1コード値を超えて外れた画素 |
| --- | --- | --- |
| 記録どおり（bt709 / limited） | 0.00201 | 0 / 82,944 |
| full を limited として読む | 0.0935 | 全部 |
| bt709 を bt601 として読む | 0.1742 | 20,736（彩度の高いバー全部） |

端数のはみ出しは 8bit の1コード（0.00392）の半分ほどで、丸めれば同じ値になる量です。
ここに色を付けると、本当に潰れている場所がそれに埋もれます。

読み方を間違えていなくても色が付く例があります。`hatch_redblue` の 4:2:0（`samples/raw`）は、
**記録どおりに読んでも 27,648 画素中 13,824 が下へ外れます**（最小 -0.069）。
1画素おきの赤と青は、間引いた時点で色差が1種類（Cb=171, Cr=179）に潰れます。
その色差と各画素の輝度を組み合わせるので、戻した値が 0 の下へ出ます。
形式と絵の組み合わせが原因で、読み方の誤りではありません。

## 面ではなく分布で見る（フェーズ2）

ツールバーの「📊 分布…」（`F7`）で別の窓が開きます。絵を眺めても
「1コード値だけずれている」「上のほうが少しだけ潰れている」「階調が思ったより少ない」は分かりません。
画素を1つずつ拾うのも現実的ではないので、**全画素を数えます**。

| 出すもの | 何のために |
| --- | --- |
| ヒストグラム（3成分） | コード値のまま数えた分布。規定範囲の境目に線を引きます |
| 波形 | 横位置ごとの分布。どこから潰れはじめているかが出ます |
| ベクトル（Cb-Cr 平面） | 色差の散らばり。原色・補色の位置を計算して重ねます |
| 数値 | 値の幅・平均・**値の種類数**・規定外の画素数・変換後に 0-1 を外れる画素数 |

集計は `RawImage.Analyze` にあり、**読み出しは `ReadCodes` の1本のまま**です。
集計用に別の読み方を書くと、絵と数字が食い違っても気付けません。
0-1 を外れた画素の数え方もプレビューの「範囲外」と同じ判定を通します（`RangeFlags`）。

**効かせるのは matrix・range・色差の戻し方だけです。** 成分の選択と段は無視します。
ここで数えたいのはRAWに入っている値そのものであって、いま出している絵ではありません。
Y' だけを表示している状態の分布を「RAW全体の分布」と読まれると、それは嘘になります。

### 自動では数え直しません

4K で 800 万画素を1周するので、一覧を送るたびに走らせると本体の操作まで重くなります。
数え直すのは「取り直す」を押したときだけです。ただし黙って古い数字を出し続けるほうが悪いので、
**対象や条件がずれたことは必ず窓に出します**（`ScopeViewModel.IsStale`）。
集計に効かない条件（成分・段）の変更では警告を出しません。意味のない警告が出続けるためです。

### ヒストグラムの縦は既定で対数です

テストパターンは一様な面を持つものが多く、そこだけ何万画素も積み上がります。
線形だと、その山以外は床に貼り付いて見えません。ここで探したいのは
「1画素だけ違う値がある」なので、既定を対数にしています。

### ベクトルの印は計算したものです

原色・補色の位置は、いまの matrix と range から計算しています（`ScopeViewModel.ColorTargets`）。
規格の図版は持っていません。

`samples/raw` の 8bit limited / BT.709 カラーバーで、計算した6点が
**RAWに実際に格納されている色差の値と完全に一致する**ことを確認しています。

| | R | Y | G | C | B | M |
| --- | --- | --- | --- | --- | --- | --- |
| 計算した (Cb, Cr) | 102, 240 | 16, 138 | 42, 26 | 154, 16 | 240, 118 | 214, 230 |
| RAWにある値 | 同じ | 同じ | 同じ | 同じ | 同じ | 同じ |

matrix を取り違えて読むと点が回転して印から外れるので、
**どの matrix で読むのが正しいかを、色を目で見ずに決められます。**

## 2枚を突き合わせる（フェーズ2）

ツールバーの「⇔ 比較…」（`F8`）で別の窓が開きます。並べて見るだけでは
「同じに見える」までしか言えません。1コード値の差は目で見えず、見えないことは
無いことの証拠になりません。**差は数えるものです。**

左は本体でいま見ているRAWと**いまの表示条件**、右は選んだ相手を**manifest の記録どおり**に読んだもの。
右まで条件を変えられるようにはしていません。両方触れると、出た差がどちらの条件のせいか言えなくなります。

| 比べる値 | 何の差か | 使える条件 |
| --- | --- | --- |
| 表示RGB（0-255） | 見え方 | 大きさが同じなら常に |
| コード値（0-255 / 0-1023） | データ | ビット深度と成分の意味が同じとき |

**大きさが違うものは比べません。** 拡大縮小して揃えると、画素は元のどちらとも違う値になり、
その差はどちらのRAWの性質でもなくなります。相手の一覧にも同じ大きさのものだけを並べます。

差の絵は成分ごとの差を R・G・B の位置へ置いたものです。**倍率を掛けないとほぼ真っ黒になる**ので
（1コード値の差は 1/255 の明るさです）、既定で8倍にし、掛けていることを絵の隣に出し続けます。
真っ黒な差の絵は「一致した」の証拠にならない（倍率が足りないだけかもしれない）ので、
一致は数値のほうで言い切ります。

差の計算も `RenderPixel` と `ReadCodes` を通ります（`RawComparison.DiffAt`）。
比較用に別の読み方を用意すると、ここでだけ一致する状態を作れてしまいます。

### 確かめたこと

`samples/raw` のうち、**同じ絵・同じ条件で格納形式だけが違う10通り**について、
コード値・表示RGBとも最大差 0、差のある画素 0 を確認しています。

| 組み合わせ | 色差 / 深度 |
| --- | --- |
| planar ↔ packed | 4:4:4 8bit、4:2:2 8bit |
| planar ↔ mipi10 | 4:4:4 / 4:2:2 / 4:2:0 10bit |
| planar ↔ p010、mipi10 ↔ p010 | 4:2:0 10bit |
| planar ↔ v210、mipi10 ↔ v210 | 4:2:2 10bit |

差が 0 のときは、倍率を 32 倍にしても差の絵が黒のままであることも確かめています。

### 段を足しても、読み出し経路は1本のままです

プレビューもピクセルプローブも `RawImage.RenderPixel` を通ります。段ごとに別の描き方を持たせると、
「絵は正しいのに数値が違う」状態に気付けなくなります。ここは
[設計上の約束](#設計上の約束)のまま変えていません。

## 表示条件の切り替え（フェーズ1）

**RAWには一切触らず、読み方だけを変えて見比べられます。**

| 切り替え | できること |
| --- | --- |
| matrix（bt601 / bt709 / bt2020） | 同じRAWを別の係数で戻したときの色ずれを見る |
| range（full / limited） | rangeを取り違えたときの黒浮き・白のくすみを見る |
| 成分（Y'・Cb・Cr または R・G・B を組み合わせて） | 選ばなかった成分を中立値に置き換えて見る。色差だけ・輝度だけを取り出せる |
| コード値（成分1つのとき） | 色変換を通さず、コード値をそのまま濃淡にする。面の値をそのまま読める |
| 色差の戻し方（最近傍 / バイリニア） | 間引かれた色差の戻し方で見え方がどう変わるかを見る |

初期値はmanifestの記録どおりです。**違う条件にしている間は画面に警告を出します。**
条件を変えたことを忘れると「RAWが壊れている」と読み違えるためです。「manifestへ戻す」で戻せます。

matrix と range は Y'CbCr のときだけ、色差の戻し方は色差が間引かれている形式のときだけ表示します。

実際の値（8bit limited / BT.709 のカラーバー、赤バー Y'=63 Cb=102 Cr=240）。

| 条件 | 表示色 |
| --- | --- |
| bt601 | `#E90002` |
| bt709（記録どおり） | `#FF0100` |
| bt2020 | `#F30000` |

白（Y'=235）を full range で読むと `#FFFFFF` が `#EBEBEB` になります。235/255 に落ちるためです。

### 色差の戻し方について

生成側（`src/vtp/subsample.py`）は色差を**平均**で間引き、**最近傍複製**で戻しています。
このアプリの「最近傍」はその戻し方をそのまま再現するもので、間引かれた粗さが四角として見えます。

「バイリニア」は平均の逆にあたる位置合わせで補間します。色差サンプル `j` の中心は輝度座標で
`j*s + (s-1)/2` にあるので、輝度位置 `x` に対応する色差の連続座標は `(x - (s-1)/2) / s` です。
この位置合わせを外すと、補間しただけで絵が半画素ずれます。

どちらが正しいという話ではありません。実際のデコーダは規格ごとに色差の位置の取り方が違うので、
**同じRAWでも戻し方で見え方が変わる**ことを示すための切り替えです。

## いまできること（フェーズ0）

WinForms版と同じことができる状態に加えて、次を新しく持ちます。

- **ニアレストネイバー拡大** — 拡大しても画素の境界がにじみません。1画素の縞や単画素のドットを、そのままの形で確認できます
- **ピクセルプローブ** — 指した画素の座標と、RAWから読んだ**生のコード値**（Y'/Cb/Cr または R/G/B）、それを変換した表示RGB8を、下のバーへ並べます
- **右クリックでコピー** — 指した画素の値を、HEX / RGB値 / 生のコード値 / 座標 / まとめて1行、から選んでクリップボードへ入れます。メニューには**実際にコピーされる文字列がそのまま並びます**（名前だけでは何が取れるのか分からないため）
- **選択 / 移動 / 拡大** — PDFビューアと同じ操作です。移動はドラッグで表示位置を動かし、拡大はホイールだけで倍率を変えます
- **パターンの説明欄** — 選んでいるパターンが何を見るための絵で、どこを見ればよいかを一覧の下に出します
- **全形式で保存** — PNG / JPEG / TIFF / BMP / GIF をまとめて出力し、形式ごとの見え方を並べて比べられます
- **列の表示切替** — 生成条件の表で、項目 / 値 / manifestキー の各列を出し入れできます（manifestキーは既定でオフ）
- **粗いサイズ絞り込み** — 実サイズの一覧が長くなるため、先頭に「〜HD」「〜FHD」「〜4K」「4K超」の区分を置いています。絞り込みは「解除」で戻せます
- **画素の境目（格子）** — 拡大しても、隣り合う画素が同じ値だと境目は見えません。「1画素の線」なのか「2画素の帯」なのかは、線を引いて初めて数えられます。色差が間引かれている形式では、**同じ色差を共有する範囲の枠**を太く重ねます（4:2:0 なら 2×2、4:2:2 なら 2×1、4:4:4 なら枠なし）。600%以上で使えます
- **画素数の通称** — 一覧とサイズ絞り込みに `640x480 VGA` のように通称を添えます。`640x480` と `720x480` は数字だけだと似ていますが、`VGA` と `SD NTSC` なら別物だと分かります。知らない大きさには何も付けません（無理に当てはめません）
- **プレビューの全画面** — 一覧・条件欄・ツールバーを畳んで絵だけにします（`F11`、`Esc` で戻る）。左右の欄は隠すだけでなく列の幅も 0 にします。隠しただけだと、絵の左右に空白の帯が残るためです
- **画素数の比での絞り込み** — 16:9 のものだけを見比べる、といった絞り方ができます。サイズ指定だと1解像度に決め打ちになります
- **パターンでの絞り込み** — パターン名で一覧を1種類に絞れます。並ぶのは、開いているフォルダに実際にあるものだけです
- **一覧の並び順** — 名前順と解像度順（小さい順／大きい順）を切り替えられます。名前で並べると `1280x720` が `176x144` より前に来ます（文字として比べるためです）。解像度順は**画素数**で比べるので、`1280x720`（92万）→ `1366x768`（105万）→ `1280x1024`（131万）のように、幅だけでは決まらないものも正しく並びます。見出し（パターン名）は並び順を変えても名前順のままです。見出しの位置まで動くと、探していたパターンを毎回追い直すことになるためです。選んだ並び順は次に開いたときも残ります
- **一覧のまとめ開閉** — パターンが増えると縦に伸びるので、見出しの右の `⊟` `⊞` でまとめて閉じる／展開できます。絞り込みを変えても開閉の状態は引き継ぎます

WinForms版に無かった格納形式として、YCbCr planar の 4:2:2 / 4:2:0（I422 / I420）にも対応しました。

WinForms版から引き継いだもの。

- manifest v1 の読み込みと、パターン名ごとの一覧表示
- 色モデル・画像サイズによる絞り込み
- 生成条件の一覧表示と、項目ごとの意味の解説
- RGB / YCbCr の planar・packed、UYVY、NV12、P010、v210、MIPI10 のプレビュー
- 10〜1600%の表示倍率、全体表示、等倍
- PNG / JPEG / TIFF / BMP / GIF 保存、RAWのコピー
- 出力先フォルダの指定と、前回開いたフォルダの復元
- 未対応形式でもmanifestは表示し、理由を出す

## ビルドと起動

```powershell
dotnet build .\apps\RawInspector\RawInspector.csproj
dotnet run --project .\apps\RawInspector\RawInspector.csproj
```

「フォルダを開く」で、RAWとmanifestのあるフォルダを指定してください。サブフォルダも走査します。

## キー操作

| キー | 動作 |
| --- | --- |
| `Ctrl+O` | フォルダを開く |
| `F5` | 開いているフォルダを読み直す（選択中のRAWと表示倍率はそのまま） |
| `Ctrl+0` | 等倍（100%）に戻す |
| `Ctrl` + `+` / `-` | 表示倍率を1段階変える（**表示領域の中央を保つ**） |
| `Ctrl` + マウスホイール | 表示倍率を変える（**カーソル下の画素を保つ**）。モードによらず効きます |
| 右クリック | 指した画素の値をコピーするメニュー |
| `Ctrl+1`〜`Ctrl+5` | PNG / JPEG / TIFF / BMP / GIF で保存 |

### 選択・移動・拡大

プレビューの操作モードは3つです。PDFビューアと同じ考え方にしています。

| モード | ドラッグ | ホイール | カーソル |
| --- | --- | --- | --- |
| ↖ 選択（既定） | — | 通常のスクロール | 矢印 |
| ✋ 移動 | 表示位置を動かす | 通常のスクロール | 手 |
| 🔍 拡大 | — | 拡大縮小（Ctrl不要） | 虫眼鏡 |

既定を選択にしているのは、ドラッグやホイールの意味が勝手に変わっていない状態から始めるためです。
`Ctrl`+ホイールはどのモードでも拡大縮小なので、モードを切り替えなくても拡大できます。

虫眼鏡カーソルはWPFの標準に無いため、`tools/make_cursor.py` で `.cur` を生成しています。

### 画素数の比は出しますが、映したときの形は名乗りません

条件の欄に「画素数の比」を出します。1920×1080 と 1280×720 がどちらも 16:9 だと分かれば、
拡大縮小しても形が崩れないと判断できます。

ただし **これは「画素が何個並んでいるか」の比であって、映したときの形の比ではありません。**
両者が一致するのは画素が正方形のときだけです。

| サイズ | 画素数の比 | 映したときの形 |
| --- | --- | --- |
| 1920×1080 | 16:9 | 16:9（画素が正方形） |
| 720×480 | **3:2** | 4:3（SDは横長の画素が前提） |
| 720×576 | **5:4** | 4:3（同上） |

どちらの前提で作られたものかは、**RAWにもmanifestにも入っていません**。
なので画素数の比だけを出して、映したときの形は名乗りません。
この区別は項目を選んだときの「この項目の意味」にも書いてあります。

### 「間引かれた」が画面のどこを指すのかを出す

色差ブロックの枠を画素の境目と分けて引いているのは、そちらのほうが読み取りたいことが多いためです。
4:2:0 なら 2×2 の画素が**同じ色差を共有**しています。枠を出せば、
「間引かれた」という言葉が画面の上のどの範囲を指すのかが目で分かります。

線は白と黒の破線を半周期ずらして重ねてあります。1色だと、その色に近い画素の上で消えるためです
（白い絵では白い線が、黒い絵では黒い線が見えません）。
ブラシ1本をタイル状に敷き詰めるので、どれだけ拡大しても図形は1組のままです。
画素ごとに線の要素を作ると、拡大したときに数万個になります。

### 倍率の上を厚くしてある理由

上限は1600%です。ここで見たいものが**1画素の単位で決まっている**ためです。

| 見たいもの | 大きさ | 100%では | 1600%なら |
| --- | --- | --- | --- |
| `hatch` の1画素縞、`linepairs` の線幅1 | 1画素 | 画面の1点 | 16点 |
| `digitalcard` の目盛りと1画素おきの縞 | 1画素 | 画面の1点 | 16点 |
| 4:2:0 の色差ブロック | 2×2画素 | 2点角 | 32点角 |

100%では「出ているのか出ていないのか」を目で確かめられません。
マウスで1画素を狙うときも、的が1点か16点かで確実さが変わります。
1920×1080を1600%にしても30,720×17,280点なので、描画上の問題はありません。

逆に**下側は注意が要ります**。縮小は最近傍で間引くので、1画素の線や点は画面から消えます。
消えているのは表示のせいでRAWから無くなったわけではないのですが、
それを知らないと「パターンが壊れている」と読み違えます。
100%未満のときは、絵の作り方の欄にその旨を出します。

### 倍率を変えたときに何を固定するか

左上を固定すると、全体表示から拡大するたびに左上隅へ飛んでしまい、見ていた場所を毎回探し直すことになります。
そのため**中央を固定**します。ボタンでもキーでも、表示領域の中央にある画素は動きません。

ただしCtrl+ホイールだけは**カーソルの下にある画素**を固定します。
気になる画素を指してからホイールを回す、という手順がそのまま通るためです。

## 画面に出ているのはRAWそのものではありません

このアプリでいちばん誤解しやすいのがここです。**プレビューは変換の結果**であって、RAWの中身そのものではありません。
そのため画面の右下に、いま見えている絵をどう作ったのかを毎回出しています。

```text
1. 格納形式 nv12 から Y' / Cb / Cr のコード値を取り出す（8bit: 0-255）
2. 間引かれた色差を輝度と同じ密度へ戻す（4:2:0 / 最近傍）
3. range=limited として正規化する
      Y  = (Y' - 16) / 219
      Cb = (Cb - 128) / 224
      Cr = (Cr - 128) / 224
4. matrix=bt709 でRGBへ戻す（Kr=0.2126, Kb=0.0722, Kg=0.7152）
      R = Y + 2(1-Kr)・Cr
      B = Y + 2(1-Kb)・Cb
      G = (Y - Kr・R - Kb・B) / Kg
5. 0-1 に丸めてから 8bit（0-255）へ量子化し、画面へ出す
```

内容は選んでいるRAWと表示条件に合わせて変わります。成分を絞っているとき、
matrix / range を manifest と違う値にしているときは、その旨も併記します。

### 成分は組み合わせて選べます

排他ではありません。**コード値のORではなく、選ばなかった成分を中立値に置き換えてから変換します。**
コード値をORしても意味のある数にならないためです。

中立値は成分ごとに違い、ここを取り違えると絵が嘘をつきます。

| 成分 | 中立値 | 0 を入れるとどうなるか |
| --- | --- | --- |
| R・G・B | 0 | 加算なので 0 が「無い」でよい |
| Cb・Cr | 128 << (bit-8) | 色差が振り切っている扱いになり、強い色かぶりになる |
| Y' | そのrangeで 0.5 のコード値 | 真っ黒になり、色差だけを見たいときに何も見えない |

これで次のような見方ができます。

- **Cb + Cr（Y'を外す）** — 輝度が中立に固定されるので、色差だけが残ります。白バーと黒バーが同じ明るさになります
- **Y' だけ** — 色差が中立に固定されるので、どの色バーも無彩色になります
- **Y' + Cb（Crを外す）** — 片方の色差軸だけを消せます
- **どれも選ばない** — 全面が中立値になり、平坦な絵になります

「コード値」を入れると色変換を通さず、コード値をそのまま濃淡にします。
画面の明るさ＝コード値／最大コード値なので、面の値をそのまま読めます。
どの成分の値を濃淡にするか決まらないので、**成分を1つだけ選んでいるときにだけ使えます**。

画面の上には「RAWの条件」として、manifestに記録された条件を項目名と値で色を分けて出します。
**上がデータの条件、右下が絵の作り方**、という対応です。

### 通称は「規格」ではなく「呼び名」として扱っています

理由が2つあります。

1つ目は**出どころがばらばら**なことです。VGA と XGA はもともと IBM の製品名、
QCIF と CIF は ITU-T のテレビ会議、NTSC / PAL は放送、HD や 4K は民生の呼び名です。
まとめて「VESA規格」と書くと事実と違います。VESA が定めているのは
DMT や CVT といった**タイミング**の表のほうです。

2つ目は、**その規格が決めているのが画素数だけではない**ことです。
DMT は画素クロック・ブランキング・同期の極性まで含みます。
ここで扱う RAW にタイミングはありません。あるのは有効画素の数だけです。

なので「この RAW は VGA 規格に準拠している」とは言えません。言えるのは
**「この画素数は VGA と呼ばれているものと同じ」**までです。表示もその言い方に留めています。

## 保存すると、表示条件が名前に残ります

同じRAWから matrix 違い・成分違いの絵を何枚も出すので、名前が同じだと後から見分けが付きません。
上書きも起きます。**条件を変えたときだけ**名前へ足すので、既定で出したものは名前が伸びません。

```
既定のまま        colorbar_ycbcr420_8bit_nv12.png
matrix を変える    colorbar_ycbcr420_8bit_nv12_bt601-limited.png
Y' だけにする      colorbar_ycbcr420_8bit_nv12_bt601-full-Y.png
コード値表示       colorbar_ycbcr420_8bit_nv12_bt601-full-Y-code.png
バイリニアへ       colorbar_ycbcr420_8bit_nv12_bt601-full-Y-code-bilinear.png
manifestへ戻す     colorbar_ycbcr420_8bit_nv12.png
```

### RAWコピーには付きません

**表示条件を変えても RAW のバイト列は変わらないためです。** 変わるのは読み方だけです。
`_bt601` の付いた RAW があると「bt601 へ変換したRAW」に見えますが、そんなものは作っていません。
名前で嘘をつくより、付けないほうが正しい状態です。

読み方を記録したものが要るなら、RAW ではなく manifest 側に足すのが筋です。
**フェーズ2で入れました**（次節）。

### 読み方を manifest として書き出す（フェーズ2）

matrix / range を manifest と違う値にしていると、「manifestへ」が押せます。
いまの読み方を、**同じRAWを指したまま** 別の manifest として書き出します。RAWは作りません。
書き出したものはその場で一覧へ取り込むので、押した直後からその条件で開けます。

書式は [`docs/manifest-v1.md`](../../docs/manifest-v1.md) の `derived_from` に決めてあります。
守っていることは4つです。

- **差し替えるのは `matrix` と `range` だけ**。成分の選択も段も書きません。
  manifest はデータの条件を書くところで、画面の見せ方を書くところではありません。
  ファイル名へ足すのも matrix と range だけです（`ViewSuffix` ではなく `InterpretationSuffix`）。
  名前に `-Y-norm` が付いていると、成分や段まで記録されていると読まれます
- **`kind: raw` 以外のファイルは外す**。プレビュー画像は差し替える前の条件で描かれた絵なので、
  新しい条件の manifest に付いていると「この条件で見るとこうなる」と読まれます。
  外したものは `dropped_files` に名前が残ります
- **`parameters_sha256` は計算し直す**。ただし書き換える前の値で計算して、元のファイルに
  入っている値と一致することを確かめてからです。確かめられないときは項目ごと外します。
  合っていないハッシュを残すのは、無いより悪い状態です
- **`generator` はそのまま**。RAWを作ったのはその生成器で、そこは変わっていません。
  manifest を書いたのが誰かは `derived_from.tool` に出ます

置き場所は**元の manifest と同じフォルダ**です。`files[].path` はそこからの相対と決まっているので、
画像の出力先フォルダへ置くとRAWを指せなくなります。

ハッシュの計算は、生成側（`json.dumps(params, sort_keys=True, ensure_ascii=False)` の SHA-256）を
C# 側で組み立て直しています。小数が入っていたら計算しません（Python と同じ文字列になると言い切れないためです）。
`samples/raw` の Y'CbCr 16件すべてで、**書き換える前の値から元のハッシュを再現できる**こと、
書き換えたあとに C# が書いた値が **Python の計算と一致する**ことを確認しています。

## 最初に出る画面

起動すると、一覧ではなく**素材の状態**が出ます。「🏠 ホーム」でいつでも戻れます
（戻っても読み込んだ一覧は消えません）。

```
素材
  generated      188 件 / 562.6 MB / パターン 42 種            [開く]
  samples/raw     21 件 / 1.7 MB   / パターン 2 種             [開く]

生成器
  video-test-patterns 0.1.0　パターン 42 種 / 成立する組み合わせ 62 通り / 格納形式 6 種

一括生成

  格納形式を網羅       tools/make_reference_raws.py    [実行]
```

アイコンは絵文字ではなく[画像を同梱](icons/)しています。絵文字はフォント任せなので、
環境によって形も色も変わり、フォントが無ければ豆腐になります。
表示は 44px です。32px より下だと格子の目・時計の針・歯車の歯が灰色に潰れます
（26 / 32 / 44 / 48px で並べて確かめました）。

**「起動するだけ」の入口にはしていません。** それだと `--help` を写しただけのものになり、
道具が増えるたびに更新漏れで古くなります。ここに出すのは、
**道具を1つずつ叩いても分からないこと**に絞っています。

- 素材がどこに何件あって、**壊れているものが無いか**。件数だけでなく、読めない manifest と
  RAW が見つからないものの数を出します。「190件あります」より
  「190件のうち2件が読めません」のほうが、次にやることが決まります
- 生成器へ繋がっているか。繋がらないことに気付くのが「生成の窓を開いたとき」だと遅いためです
- 一括生成を、**作る前に件数と容量を見てから**走らせられるか。300MB 近くになるものがあります
  （見積りを持つ道具だけボタンを有効にします。持たない道具に付けても効きません）

リポジトリの場所は、実行ファイルから上へ辿って探します（`pyproject.toml` と
`src/vtp/patterns.py` の両方がある場所）。相対の段数を決め打ちすると、
出力先を変えただけで見失います。見つからないときは、黙って動かないのではなく
見つからなかったと出します。

## パターンを生成する

ツールバーの **「＋ 生成…」** で生成の窓が開きます。条件を選んで生成すると、
できた RAW をそのまま一覧へ取り込んで選択します。**作る→すぐ見るが1周します。**

### 画素を作るのはPython側です

このアプリは生成しません。`python -m vtp` を呼ぶだけです。
C# 側にも生成を書くと、同じ仕様の実装が2つになり、片方だけ直したときに黙ってずれます。
検証の土台そのものが崩れるので、実装は1つに保ちます。

### 選べる条件も生成器から取ります

「v210 は幅が6の倍数」「p010 は上位詰めのみ」といった規則を C# 側へ書き写すと、
生成器を直したときにずれます。ずれ方は「GUIでは作れるのに生成器が弾く」か、その逆で、
どちらも原因を探しにくい形で出ます。

そこで生成器に `--describe` を足しました。**成立する組み合わせを数え上げて JSON で返します。**

```sh
python -m vtp --describe
```

この表は規則を書き出したものではなく、`validate()` を実際に通して作っています。
幅・高さの倍数も、**通る最小の値を探して**求めています（制約はどれも「Nの倍数」の形なので、
通る最小値がそのまま N です）。正解は `config.py` の1箇所だけに留まります。

### 成立しない組み合わせは、消さずに理由を出します

選択肢を黙って減らすと、なぜ消えたのかが分かりません。選べるままにして、
成立しない理由と、次に何を変えればよいかを出します。

```
この組み合わせは成立しません。nv12 で使えるのは 色モデル ycbcr、色差 4:2:0、8bit、… です。
この条件では幅が 6 の倍数、高さが 1 の倍数である必要があります（指定: 1921 x 1080）。
近い値は 1920 x 1080 です。
```

実行するコマンドもそのまま出します。貼れば端末でも同じことができます。
生成器が断ったときは、その文面をこちらで言い換えずに出します。
言い換えると、生成器が実際に何を嫌がったのかが分からなくなります。

## 生値と変換値の区別

このアプリが画面に出す数値は2種類あります。混同すると読み違えるので、表示でも分けています。

| | 何の値か | 範囲 |
| --- | --- | --- |
| **コード値** | RAWのバイト列から取り出した**生の値**。変換していません | 8bitなら 0–255、10bitなら 0–1023 |
| **変換後（HEX / RGB）** | matrixとrangeを適用し、8bitへ丸めた**表示用の値** | 常に 0–255 |

プレビュー画像そのものは **RGB888**（Bgra32）です。10bitのRAWでも、画面に出る時点では8bitへ落ちています。
階調を落とさずに見たいときはコード値のほうを読んでください。

4:2:0 / 4:2:2 の Cb・Cr は、**その画素が共有している間引き後のサンプル**をそのまま返します（補間していません）。
隣り合う2画素や4画素で同じ値が出るのは、色差がそこにしか無いためです。

## 設計上の約束

**プレビューとピクセルプローブは、必ず同じ読み出し経路を通します。**
`RawImage.ReadCodes()` が唯一のコード値の出どころで、画面に出す絵もプローブが返す数値もここから作ります。デコード済みの画素を別に持たせると、「絵は正しいのに数値が違う」状態に気付けなくなるためです。

色の解釈（matrix・range）は `ColorInterpretation` として独立させてあります。manifestの値を初期値にしつつ、あとから別の解釈で読み直せるようにするためです。

**画素の読み取り表示はウィンドウ最下部のバーに固定しています。** 各欄の幅と帯の高さを固定してあるのは、
カーソルを動かすたびに文字数が変わって桁位置や高さが動くと、その上のプレビュー枠までずれるためです。
プレビュー欄の中ではなく全幅のバーに置いたのは、中央パネルを狭めても全ての欄が入りきるようにするためです。

**「いま指している値」と「コピー対象の値」は別に持っています。**
下のバーは前者で、カーソルがプレビューから外れたら消します（抜けぎわの画素が残っていると、
いま指している値だと読み違えるためです）。右クリックメニューは後者で、外れても残します。
1組にすると、メニューへマウスを移した瞬間に `MouseLeave` が飛んで中身が全部「—」に戻ってしまいます。

**ツールバーは折り返しません。** WrapPanelだと、ウィンドウ幅や隠れているグループの有無で
折り返し位置が変わり、同じ場所を押しているつもりで違うボタンを押すことになります。
行を固定し、狭いときは折り返さずに横スクロールさせます。

**ツールバーの高さと位置は固定です。** 色モデルやサブサンプリングによって使えない操作
（matrix / range、色差の戻し方）がありますが、そこは `Collapsed` ではなく `Hidden` にして
場所を確保したままにしています。詰めてしまうと、選んだRAWによって他のボタンの位置や
ツールバーの行数まで変わり、同じ場所を押しているつもりで違うものを押すことになるためです。

manifestと違う条件で見ているときの警告も、ツールバーではなく**プレビュー面へ重ねて**出します。
ツールバーの中に置くと、出たり消えたりするたびに枠の高さが変わってしまいます。

**生成条件の表は、確認する順に並べています。** パターン名 → 画像サイズ → 色モデル →
色差サブサンプリング → ビット深度、という優先度です。列見出しを押せば昇順・降順に並び替えられますが、
押した状態が残ると「なぜこの順なのか」が分からなくなるので、「既定に戻す」で並びと列の表示を戻せます。

**ボタンの色は3系統だけに絞っています。** 青は「その画面で最初にやること」（フォルダを開く）、
緑は「変換して書き出す」、ベージュは「RAWをそのままコピー」。それ以外は色を付けません。
色が増えるほど、どれが主要な操作なのかが読めなくなるためです。
関連する操作は薄い枠でまとめ、横一列に並ぶボタンのどれとどれが仲間なのかを示しています。

**一覧と表の選択色は自前で指定しています。** 既定のままだとシステムの反転色（白文字）になり、
明るい選択背景の上で文字が読めなくなるためです。

**「この項目の意味」は高さを固定しています。** 説明の行数で枠が伸び縮みすると、
項目を選ぶたびに下のパネルまで動いてしまいます。

**「表示中の絵の作り方」だけ、他のパネルと色を変えています。**
「いま見えているものはRAWではない」という注意書きなので、他の情報と同じ見た目だと読み飛ばされます。

**パターンの説明は `Models/PatternGuide.cs` に置いています。** 絵を見ただけでは何のための形か分かりません。
パターンは目的が先にあって形が決まっているので、目的と「どこを見るか」をコード側に持たせ、
生成側（`src/vtp/patterns.py`）と同じ内容を1か所で書けるようにしています。

画面ごとの使い方は [`docs/usage/`](../../docs/usage/) にあります。`F1` と各画面の「？」で開きます。

| 入口 | 開くもの |
| --- | --- |
| `F1`、ツールバーの「？」 | いま出ている画面（HOME なら [launcher.md](../../docs/usage/launcher.md)、ビューアなら [viewer.md](../../docs/usage/viewer.md)） |
| HOME の各カードの「使い方」 | そのカードに対応する1枚 |
| 生成の窓の「？」 | [generator.md](../../docs/usage/generator.md) |

**実体は `docs/` の1か所だけです。** README とツールチップに同じ話を書くと、
片方だけ直したときに黙ってずれます。README は開発者向け（ビルド・設計の理由）、
`docs/usage/` は操作手順、という分担です。

配布のされ方が2通りあるので、探す場所も2通り持っています。

1. リポジトリの `docs/` — そちらが実体なので先に見ます
2. 実行ファイルの隣の `docs/` — csproj の `Content` がビルド時に複製します
3. 実行ファイルへの埋め込み — 1も2も無いとき（exe だけを持ち出した場合）の保険です

文書を1枚増やすときは、`docs/usage/` へ置いて `Models/HelpLibrary.cs` の `Contents` へ追記します。
`docs/` を走査して自動で並べないのは、並び順がファイル名まかせになり、読む順番と関係なくなるためです。
csproj 側はワイルドカードなので、追加の指定は要りません。

表示は `MarkdownRenderer` が行います。**完全なMarkdown実装ではありません。**
`docs/` で実際に使っている記法（見出し・箇条書き・番号付き・表・コードブロック・強調・
インラインコード・リンク・区切り線）だけを見ます。足りなくなったら、記法を増やす前に
文書のほうを直すほうが早いはずです。

## アイコンとカーソル

どちらも生成スクリプトを置いています。外部素材は使っていません。

```powershell
python tools/make_icon.py --png-preview generated/icon_preview.png     # app.ico
python tools/make_cursor.py --png-preview generated/cursor_preview.png # zoom.cur
```

アイコンの図案はカラーバーとルーペで、ルーペの中はバーが拡大されて見えます。
16px・24px はカラーバーだけにしています。小さいサイズでルーペを入れると、
レンズの中が1色で埋まってただの丸に見えるためです。

カーソルは白い線に濃い縁を付けてあります。明るいパターンの上でも暗いパターンの上でも見えるようにするためです。
`.cur` は `.ico` とほぼ同じ構造なので、Pillowで `.ico` を書き出してから種別とホットスポットの2か所だけ書き換えています。

## 検証

`generated/` の全形式について、このアプリのデコード結果とPython側が出した `*.preview.png` が**1バイトも違わない**ことを確認しています（v210・MIPI10・P010・NV12・I420を含む）。

確認用のサンプルは次で作れます。

```powershell
python tools/make_samples.py         # 全パターンを1本ずつ（形式とサイズを散らす）
python tools/make_variant_raws.py    # 1つのパターンを条件で振る（塗り違い・サイズ違い）
```

サイズを揃えないのは、幅や高さに依存する不具合を丸い数字で隠さないためです。
実際この一式を作ったことで、**YCbCr planar の 4:2:0 がプレビューできない**という穴が見つかりました。

条件を振ったほうは、152件すべてで最大差 0 を確認しています。
うち `raster` を 4:4:4 / 4:2:2 / 4:2:0 で出した3本は、**間引きの有無にかかわらず一致**します。
一様な面には色差の細かい変化が無いためで、ここに差が出るなら原因は間引きではなく色変換側です。

ピクセルプローブの値も手計算と突き合わせています。8bit limited range・BT.709 のカラーバーで、白の `Y'=235`、黒の `Y'=16`、赤の `Y'=63`（= 16 + 219 × 0.2126 の丸め）。
