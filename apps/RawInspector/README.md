# RawInspector

`video-test-patterns` が生成したRAWを、manifestとセットで**検査する**ためのWPFアプリです。

[`RawManifestViewer`](../RawManifestViewer/)（Windows Forms）の後継にあたります。
あちらは「生成したRAWを開いて見る」ためのものでした。こちらは、画素のコード値・変換条件・中間データまで踏み込んで確認することを目的にしています。

## 表示条件の切り替え（フェーズ1）

**RAWには一切触らず、読み方だけを変えて見比べられます。**

| 切り替え | できること |
| --- | --- |
| matrix（bt601 / bt709 / bt2020） | 同じRAWを別の係数で戻したときの色ずれを見る |
| range（full / limited） | rangeを取り違えたときの黒浮き・白のくすみを見る |
| 成分（Y'・Cb・Cr または R・G・B を組み合わせて） | 選ばなかった成分を中立値に置き換えて見る。色差だけ・輝度だけを取り出せる |
| コード値（成分1つのとき） | 色変換を通さず、コード値をそのまま濃淡にする。面の値をそのまま読める |
| 色差の戻し方（最近傍 / バイリニア） | 間引かれた色差の戻し方で見え方がどう変わるかを見る |

初期値はmanifestの記録どおりです。**違う条件にしている間は画面に警告を出します。**
条件を変えたことを忘れると「RAWが壊れている」と読み違えるためです。「manifestへ戻す」で戻せます。

matrix と range は Y'CbCr のときだけ、色差の戻し方は色差が間引かれている形式のときだけ表示します。

実際の値（8bit limited / BT.709 のカラーバー、赤バー Y'=63 Cb=102 Cr=240）。

| 条件 | 表示色 |
| --- | --- |
| bt601 | `#E90002` |
| bt709（記録どおり） | `#FF0100` |
| bt2020 | `#F30000` |

白（Y'=235）を full range で読むと `#FFFFFF` が `#EBEBEB` になります。235/255 に落ちるためです。

### 色差の戻し方について

生成側（`src/vtp/subsample.py`）は色差を**平均**で間引き、**最近傍複製**で戻しています。
このアプリの「最近傍」はその戻し方をそのまま再現するもので、間引かれた粗さが四角として見えます。

「バイリニア」は平均の逆にあたる位置合わせで補間します。色差サンプル `j` の中心は輝度座標で
`j*s + (s-1)/2` にあるので、輝度位置 `x` に対応する色差の連続座標は `(x - (s-1)/2) / s` です。
この位置合わせを外すと、補間しただけで絵が半画素ずれます。

どちらが正しいという話ではありません。実際のデコーダは規格ごとに色差の位置の取り方が違うので、
**同じRAWでも戻し方で見え方が変わる**ことを示すための切り替えです。

## いまできること（フェーズ0）

WinForms版と同じことができる状態に加えて、次を新しく持ちます。

- **ニアレストネイバー拡大** — 拡大しても画素の境界がにじみません。1画素の縞や単画素のドットを、そのままの形で確認できます
- **ピクセルプローブ** — 指した画素の座標と、RAWから読んだ**生のコード値**（Y'/Cb/Cr または R/G/B）、それを変換した表示RGB8を、下のバーへ並べます
- **右クリックでコピー** — 指した画素の値を、HEX / RGB値 / 生のコード値 / 座標 / まとめて1行、から選んでクリップボードへ入れます。メニューには**実際にコピーされる文字列がそのまま並びます**（名前だけでは何が取れるのか分からないため）
- **選択 / 移動 / 拡大** — PDFビューアと同じ操作です。移動はドラッグで表示位置を動かし、拡大はホイールだけで倍率を変えます
- **パターンの説明欄** — 選んでいるパターンが何を見るための絵で、どこを見ればよいかを一覧の下に出します
- **全形式で保存** — PNG / JPEG / TIFF / BMP / GIF をまとめて出力し、形式ごとの見え方を並べて比べられます
- **列の表示切替** — 生成条件の表で、項目 / 値 / manifestキー の各列を出し入れできます（manifestキーは既定でオフ）
- **粗いサイズ絞り込み** — 実サイズの一覧が長くなるため、先頭に「〜HD」「〜FHD」「〜4K」「4K超」の区分を置いています。絞り込みは「解除」で戻せます
- **画素数の通称** — 一覧とサイズ絞り込みに `640x480 VGA` のように通称を添えます。`640x480` と `720x480` は数字だけだと似ていますが、`VGA` と `SD NTSC` なら別物だと分かります。知らない大きさには何も付けません（無理に当てはめません）
- **一覧の並び順** — 名前順と解像度順（小さい順／大きい順）を切り替えられます。名前で並べると `1280x720` が `176x144` より前に来ます（文字として比べるためです）。解像度順は**画素数**で比べるので、`1280x720`（92万）→ `1366x768`（105万）→ `1280x1024`（131万）のように、幅だけでは決まらないものも正しく並びます。見出し（パターン名）は並び順を変えても名前順のままです。見出しの位置まで動くと、探していたパターンを毎回追い直すことになるためです。選んだ並び順は次に開いたときも残ります
- **一覧のまとめ開閉** — パターンが増えると縦に伸びるので、見出しの右の `⊟` `⊞` でまとめて閉じる／展開できます。絞り込みを変えても開閉の状態は引き継ぎます

WinForms版に無かった格納形式として、YCbCr planar の 4:2:2 / 4:2:0（I422 / I420）にも対応しました。

WinForms版から引き継いだもの。

- manifest v1 の読み込みと、パターン名ごとの一覧表示
- 色モデル・画像サイズによる絞り込み
- 生成条件の一覧表示と、項目ごとの意味の解説
- RGB / YCbCr の planar・packed、UYVY、NV12、P010、v210、MIPI10 のプレビュー
- 10〜400%の表示倍率、全体表示、等倍
- PNG / JPEG / TIFF / BMP / GIF 保存、RAWのコピー
- 出力先フォルダの指定と、前回開いたフォルダの復元
- 未対応形式でもmanifestは表示し、理由を出す

## ビルドと起動

```powershell
dotnet build .\apps\RawInspector\RawInspector.csproj
dotnet run --project .\apps\RawInspector\RawInspector.csproj
```

「フォルダを開く」で、RAWとmanifestのあるフォルダを指定してください。サブフォルダも走査します。

## キー操作

| キー | 動作 |
| --- | --- |
| `Ctrl+O` | フォルダを開く |
| `F5` | 開いているフォルダを読み直す（選択中のRAWと表示倍率はそのまま） |
| `Ctrl+0` | 等倍（100%）に戻す |
| `Ctrl` + `+` / `-` | 表示倍率を1段階変える（**表示領域の中央を保つ**） |
| `Ctrl` + マウスホイール | 表示倍率を変える（**カーソル下の画素を保つ**）。モードによらず効きます |
| 右クリック | 指した画素の値をコピーするメニュー |
| `Ctrl+1`〜`Ctrl+5` | PNG / JPEG / TIFF / BMP / GIF で保存 |

### 選択・移動・拡大

プレビューの操作モードは3つです。PDFビューアと同じ考え方にしています。

| モード | ドラッグ | ホイール | カーソル |
| --- | --- | --- | --- |
| ↖ 選択（既定） | — | 通常のスクロール | 矢印 |
| ✋ 移動 | 表示位置を動かす | 通常のスクロール | 手 |
| 🔍 拡大 | — | 拡大縮小（Ctrl不要） | 虫眼鏡 |

既定を選択にしているのは、ドラッグやホイールの意味が勝手に変わっていない状態から始めるためです。
`Ctrl`+ホイールはどのモードでも拡大縮小なので、モードを切り替えなくても拡大できます。

虫眼鏡カーソルはWPFの標準に無いため、`tools/make_cursor.py` で `.cur` を生成しています。

### 倍率を変えたときに何を固定するか

左上を固定すると、全体表示から拡大するたびに左上隅へ飛んでしまい、見ていた場所を毎回探し直すことになります。
そのため**中央を固定**します。ボタンでもキーでも、表示領域の中央にある画素は動きません。

ただしCtrl+ホイールだけは**カーソルの下にある画素**を固定します。
気になる画素を指してからホイールを回す、という手順がそのまま通るためです。

## 画面に出ているのはRAWそのものではありません

このアプリでいちばん誤解しやすいのがここです。**プレビューは変換の結果**であって、RAWの中身そのものではありません。
そのため画面の右下に、いま見えている絵をどう作ったのかを毎回出しています。

```text
1. 格納形式 nv12 から Y' / Cb / Cr のコード値を取り出す（8bit: 0-255）
2. 間引かれた色差を輝度と同じ密度へ戻す（4:2:0 / 最近傍）
3. range=limited として正規化する
      Y  = (Y' - 16) / 219
      Cb = (Cb - 128) / 224
      Cr = (Cr - 128) / 224
4. matrix=bt709 でRGBへ戻す（Kr=0.2126, Kb=0.0722, Kg=0.7152）
      R = Y + 2(1-Kr)・Cr
      B = Y + 2(1-Kb)・Cb
      G = (Y - Kr・R - Kb・B) / Kg
5. 0-1 に丸めてから 8bit（0-255）へ量子化し、画面へ出す
```

内容は選んでいるRAWと表示条件に合わせて変わります。成分を絞っているとき、
matrix / range を manifest と違う値にしているときは、その旨も併記します。

### 成分は組み合わせて選べます

排他ではありません。**コード値のORではなく、選ばなかった成分を中立値に置き換えてから変換します。**
コード値をORしても意味のある数にならないためです。

中立値は成分ごとに違い、ここを取り違えると絵が嘘をつきます。

| 成分 | 中立値 | 0 を入れるとどうなるか |
| --- | --- | --- |
| R・G・B | 0 | 加算なので 0 が「無い」でよい |
| Cb・Cr | 128 << (bit-8) | 色差が振り切っている扱いになり、強い色かぶりになる |
| Y' | そのrangeで 0.5 のコード値 | 真っ黒になり、色差だけを見たいときに何も見えない |

これで次のような見方ができます。

- **Cb + Cr（Y'を外す）** — 輝度が中立に固定されるので、色差だけが残ります。白バーと黒バーが同じ明るさになります
- **Y' だけ** — 色差が中立に固定されるので、どの色バーも無彩色になります
- **Y' + Cb（Crを外す）** — 片方の色差軸だけを消せます
- **どれも選ばない** — 全面が中立値になり、平坦な絵になります

「コード値」を入れると色変換を通さず、コード値をそのまま濃淡にします。
画面の明るさ＝コード値／最大コード値なので、面の値をそのまま読めます。
どの成分の値を濃淡にするか決まらないので、**成分を1つだけ選んでいるときにだけ使えます**。

画面の上には「RAWの条件」として、manifestに記録された条件を項目名と値で色を分けて出します。
**上がデータの条件、右下が絵の作り方**、という対応です。

### 通称は「規格」ではなく「呼び名」として扱っています

理由が2つあります。

1つ目は**出どころがばらばら**なことです。VGA と XGA はもともと IBM の製品名、
QCIF と CIF は ITU-T のテレビ会議、NTSC / PAL は放送、HD や 4K は民生の呼び名です。
まとめて「VESA規格」と書くと事実と違います。VESA が定めているのは
DMT や CVT といった**タイミング**の表のほうです。

2つ目は、**その規格が決めているのが画素数だけではない**ことです。
DMT は画素クロック・ブランキング・同期の極性まで含みます。
ここで扱う RAW にタイミングはありません。あるのは有効画素の数だけです。

なので「この RAW は VGA 規格に準拠している」とは言えません。言えるのは
**「この画素数は VGA と呼ばれているものと同じ」**までです。表示もその言い方に留めています。

## 生値と変換値の区別

このアプリが画面に出す数値は2種類あります。混同すると読み違えるので、表示でも分けています。

| | 何の値か | 範囲 |
| --- | --- | --- |
| **コード値** | RAWのバイト列から取り出した**生の値**。変換していません | 8bitなら 0–255、10bitなら 0–1023 |
| **変換後（HEX / RGB）** | matrixとrangeを適用し、8bitへ丸めた**表示用の値** | 常に 0–255 |

プレビュー画像そのものは **RGB888**（Bgra32）です。10bitのRAWでも、画面に出る時点では8bitへ落ちています。
階調を落とさずに見たいときはコード値のほうを読んでください。

4:2:0 / 4:2:2 の Cb・Cr は、**その画素が共有している間引き後のサンプル**をそのまま返します（補間していません）。
隣り合う2画素や4画素で同じ値が出るのは、色差がそこにしか無いためです。

## 設計上の約束

**プレビューとピクセルプローブは、必ず同じ読み出し経路を通します。**
`RawImage.ReadCodes()` が唯一のコード値の出どころで、画面に出す絵もプローブが返す数値もここから作ります。デコード済みの画素を別に持たせると、「絵は正しいのに数値が違う」状態に気付けなくなるためです。

色の解釈（matrix・range）は `ColorInterpretation` として独立させてあります。manifestの値を初期値にしつつ、あとから別の解釈で読み直せるようにするためです。

**画素の読み取り表示はウィンドウ最下部のバーに固定しています。** 各欄の幅と帯の高さを固定してあるのは、
カーソルを動かすたびに文字数が変わって桁位置や高さが動くと、その上のプレビュー枠までずれるためです。
プレビュー欄の中ではなく全幅のバーに置いたのは、中央パネルを狭めても全ての欄が入りきるようにするためです。

**「いま指している値」と「コピー対象の値」は別に持っています。**
下のバーは前者で、カーソルがプレビューから外れたら消します（抜けぎわの画素が残っていると、
いま指している値だと読み違えるためです）。右クリックメニューは後者で、外れても残します。
1組にすると、メニューへマウスを移した瞬間に `MouseLeave` が飛んで中身が全部「—」に戻ってしまいます。

**ツールバーは折り返しません。** WrapPanelだと、ウィンドウ幅や隠れているグループの有無で
折り返し位置が変わり、同じ場所を押しているつもりで違うボタンを押すことになります。
行を固定し、狭いときは折り返さずに横スクロールさせます。

**ツールバーの高さと位置は固定です。** 色モデルやサブサンプリングによって使えない操作
（matrix / range、色差の戻し方）がありますが、そこは `Collapsed` ではなく `Hidden` にして
場所を確保したままにしています。詰めてしまうと、選んだRAWによって他のボタンの位置や
ツールバーの行数まで変わり、同じ場所を押しているつもりで違うものを押すことになるためです。

manifestと違う条件で見ているときの警告も、ツールバーではなく**プレビュー面へ重ねて**出します。
ツールバーの中に置くと、出たり消えたりするたびに枠の高さが変わってしまいます。

**生成条件の表は、確認する順に並べています。** パターン名 → 画像サイズ → 色モデル →
色差サブサンプリング → ビット深度、という優先度です。列見出しを押せば昇順・降順に並び替えられますが、
押した状態が残ると「なぜこの順なのか」が分からなくなるので、「既定に戻す」で並びと列の表示を戻せます。

**ボタンの色は3系統だけに絞っています。** 青は「その画面で最初にやること」（フォルダを開く）、
緑は「変換して書き出す」、ベージュは「RAWをそのままコピー」。それ以外は色を付けません。
色が増えるほど、どれが主要な操作なのかが読めなくなるためです。
関連する操作は薄い枠でまとめ、横一列に並ぶボタンのどれとどれが仲間なのかを示しています。

**一覧と表の選択色は自前で指定しています。** 既定のままだとシステムの反転色（白文字）になり、
明るい選択背景の上で文字が読めなくなるためです。

**「この項目の意味」は高さを固定しています。** 説明の行数で枠が伸び縮みすると、
項目を選ぶたびに下のパネルまで動いてしまいます。

**「表示中の絵の作り方」だけ、他のパネルと色を変えています。**
「いま見えているものはRAWではない」という注意書きなので、他の情報と同じ見た目だと読み飛ばされます。

**パターンの説明は `Models/PatternGuide.cs` に置いています。** 絵を見ただけでは何のための形か分かりません。
パターンは目的が先にあって形が決まっているので、目的と「どこを見るか」をコード側に持たせ、
生成側（`src/vtp/patterns.py`）と同じ内容を1か所で書けるようにしています。

レンズの中が1色で埋まってただの丸に見えるためです。

## 検証

`generated/` の全形式について、このアプリのデコード結果とPython側が出した `*.preview.png` が**1バイトも違わない**ことを確認しています（v210・MIPI10・P010・NV12・I420を含む）。

確認用のサンプルは次で作れます。

```powershell
python tools/make_samples.py         # 全パターンを1本ずつ（形式とサイズを散らす）
python tools/make_variant_raws.py    # 1つのパターンを条件で振る（塗り違い・サイズ違い）
```

サイズを揃えないのは、幅や高さに依存する不具合を丸い数字で隠さないためです。
実際この一式を作ったことで、**YCbCr planar の 4:2:0 がプレビューできない**という穴が見つかりました。

条件を振ったほうは、152件すべてで最大差 0 を確認しています。
うち `raster` を 4:4:4 / 4:2:2 / 4:2:0 で出した3本は、**間引きの有無にかかわらず一致**します。
一様な面には色差の細かい変化が無いためで、ここに差が出るなら原因は間引きではなく色変換側です。

ピクセルプローブの値も手計算と突き合わせています。8bit limited range・BT.709 のカラーバーで、白の `Y'=235`、黒の `Y'=16`、赤の `Y'=63`（= 16 + 219 × 0.2126 の丸め）。
